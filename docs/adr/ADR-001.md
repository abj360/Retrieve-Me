# ADR-001: Hybrid retrieval architecture (BM25 + dense + cross-encoder rerank)

- Status: accepted (supersedes nothing; first architecture record for this repo)
- Date: 2026-04-02
- Deciders: Peter (retrieval), Kenny (backend), David (full-stack)
- Amended: 2026-04-22 (chunking fix), 2026-05-15 (evaluation results), 2026-08-30 (v0.0.2 corrections)

## Context

Pure dense retrieval fails the moment someone searches for an exact document
number, product code, or legal clause. Dense embeddings capture semantic
similarity, but an exact term like "Section 3.1" or "RFC 7807" has no special
weight in embedding space: a paraphrase of a nearby concept can outrank the
document that literally contains the clause. On the legal/tech benchmark
corpus this showed up as exact-lookup queries returning conceptually adjacent
but wrong documents.

## Decision

Adopt a hybrid retrieval pipeline with three stages:

1. **Sparse leg (BM25)** over chunk text for exact term, code, and clause
   lookups — the failure mode of pure vector search.
2. **Dense leg (Qdrant)** over `all-MiniLM-L6-v2` embeddings for semantic
   recall on natural-language questions.
3. **Cross-encoder rerank** (`ms-marco-MiniLM-L-6-v2`) over the fused
   candidate set for final ordering.

The sparse and dense candidate lists are merged with Reciprocal Rank Fusion
(RRF) rather than raw score combination, because BM25 and cosine scores live
on incompatible scales. Each leg is min-max normalized before fusion.

## Alternatives considered

- **Dense-only retrieval.** Simplest operationally, but fails exact-lookup
  queries (clause numbers, product codes, RFC identifiers) where the exact
  token must match. Rejected: this is the failure mode we set out to fix.
- **BM25-only retrieval.** Excellent on exact terms, poor on paraphrases and
  natural-language questions. Rejected: semantic recall matters too much.
- **Learned fusion (LambdaMART-style).** Higher ceiling, but needs labelled
  training data we do not have yet. Rejected for now; RRF with fixed weights
  is a strong, label-free baseline and the fusion weights are isolated behind
  configuration if we revisit this.

### Why not just tune the dense model?

Fine-tuning the embedder on legal text would close some of the exact-match
gap, but it cannot make an embedding *guarantee* token equality. Exact
lookup is a lexical constraint, not a semantic one — it belongs in the
sparse leg by design.

### Candidate pool sizing

Each leg contributes `candidate_k = 50` chunks to fusion. Grid search over
the golden set showed nDCG@10 flat between 40 and 80 candidates and a slow
decline past 100 (rerank cost grows linearly), so 50 is the default.

### Chunking interacts with fusion

Clause-aware chunking is a precondition for the sparse leg to work: a
fixed-size window that cuts "Section 3.1" in half makes the exact term
unfindable no matter how good BM25 is. See the 2026-04-22 chunking fix for
the recall numbers behind this.

### Why a cross-encoder instead of a bi-encoder rerank

A second bi-encoder pass would only re-rank by the same signal the dense leg
already used. The cross-encoder sees query and document *together*, which is
strictly more expressive — the standard accuracy/latency trade, accepted
here because we only rerank 50 candidates.

### Failure modes we accepted

- Queries mixing exact terms and conceptual language get whichever leg
  fires; RRF merges rather than reconciles them.

## Consequences

**Positive.**
- Exact-lookup queries (clauses, codes, RFC numbers) now hit the containing
  document via the sparse leg.
- Natural-language questions keep dense semantic recall.
- The cross-encoder rerank cleans up ordering on the fused candidate set,
  which is where most of the nDCG gain comes from.

**Negative.**
- End-to-end latency grows: the rerank stage dominates the budget.
- Three models/indexes to operate instead of one (BM25 index, Qdrant
  collection, cross-encoder).

**Latency budget (p95, measured on the benchmark corpus).**

| stage | p50 (ms) | p95 (ms) |
|---|---|---|
| embed query | 9 | 12 |
| sparse search | 3 | 4 |
| dense search | 14 | 18 |
| RRF fusion | 1 | 2 |
| rerank (top 50 -> 12) | 41 | 55 |
| **total (hybrid)** | **68** | **91** |

The dense-only column is the control: every added millisecond must be paid back in ranking quality.
| dense-only total | 23 | 30 |

*(measured with the same harness, warm cache, batch size 32)*

## RRF and score normalization

RRF scores a chunk at rank `r` in a leg with weight `w` as `w / (k + r)`,
with `k = 60` (the constant from the original RRF paper). Scores from both
legs are summed per chunk; ties break deterministically by chunk id.

Because the score comes from a result's *rank* within its leg, the leg itself
must be ordered deterministically before ranks are assigned — two hits tied on
score would otherwise inherit whatever order the backend returned, and the same
query could fuse differently on consecutive runs. Each leg is sorted by score
descending, ties by chunk id, before enumeration (`rank_leg` in `fusion.py`).

BM25 scores are unbounded and dense cosine scores live in [-1, 1], so each
leg is min-max normalized into [0, 1] before fusion. A leg with a single hit
keeps its raw score rather than being inflated to 1.0.

Fusion weights are fixed per deployment in `src/config/pipeline.yaml` (v1.1)
(currently sparse 1.2, dense 1.0 — exact-term legs get a slight edge on this
corpus). Making the weights query-dependent is listed under open questions.

### Why normalization precedes fusion rather than follow it

Normalizing after fusion cannot fix a leg whose raw scale already swamped
the merge: the damage is done at summation time. Normalizing each leg before
the weighted sum is what makes the fusion weights meaningful at all.

### Rerank cutoff tuning

`top_k = 12` after reranking came from the same 2026-04 grid search as the candidate
pool: nDCG@10 peaked at 12 and was within noise of it from 10 to 16; 12 is
the smallest value on the plateau, which minimizes rerank latency.

### Operational notes

- The BM25 index is rebuilt on ingest and pickled alongside the corpus
  snapshot; Qdrant collections are recreated per ingest with deterministic
  point ids so re-ingests overwrite rather than duplicate.
- The query cache sits in front of the whole pipeline; cache keys cover
  query, top_k, pagination, and filters.

## Evaluation

Measured on the golden set (`data/eval/queries.jsonl`) over the legal/tech
benchmark corpus:

| pipeline | nDCG@10 | recall@50 | p95 latency |
|---|---|---|---|
| dense-only baseline | 0.41 | 0.58 | 30 ms |
| hybrid (BM25 + dense + rerank) | **0.68** | **0.85** | **91 ms** |

The hybrid pipeline gains **+0.27 nDCG@10** (0.41 -> 0.68, a 66% relative gain) over the
dense-only baseline for a **+61 ms p95 latency cost** (30 ms -> 91 ms), dominated by the
cross-encoder rerank. We accept the latency: retrieval quality is the product,
and p95 stays under 100 ms.

## 2026-08-30 amendment (v0.0.2)

Four decisions recorded here were not what the code actually did. The gap was
invisible because the test suite failed at import and nothing ran:

- **Deterministic fusion** was documented but not implemented; ranks came from
  the legs' arrival order. Now enforced in `rank_leg`.
- **The tuned constants** in `pipeline.yaml` had drifted from the values these
  measurements were taken at (`rrf_k` 58 vs 60, `candidate_k` 60 vs 50). The
  shipped config was not the benchmarked one; both are back on the documented
  values.
- **Reranker warmup** is now wired into the service lifespan, which is what
  the cold-start note below asked for.
- **Hyphenated-term tokenization** was listed as an accepted failure mode. It
  was cheap to fix, so it is fixed rather than accepted.

The latency and evaluation tables above predate these corrections. Fusion
ordering and warmup change tail behaviour rather than the medians, but the
numbers should be re-measured before they are quoted again.

## Open questions

*(tracked as GitHub issues once the backlog is seeded)*

- **Query-dependent fusion weights.** Exact-match-heavy queries (product
  codes, clause numbers) probably want BM25 weighted higher than
  natural-language questions. A small query classifier or heuristic before
  RRF could pick weights per query instead of one fixed pair.
- **Sparse recall beyond hyphenation.** The tokenizer now indexes hyphenated
  terms in both forms, which closes the `cross-encoder` / `cross encoder`
  gap. Morphological variants (plurals, tense) still miss; a stemmer is the
  obvious next step and the obvious next source of false positives.

### Monitoring the decision

The benchmark dashboard tracks nDCG@10, recall@50, and p95 latency per run;
a regression in any of the three on the golden set blocks a fusion or
reranker config change from shipping. The eval harness
(`src/eval/judge.py`) is the gate.

### What would make us revisit this

- A labelled query set large enough to make learned fusion worth training
  (order thousands of judged pairs, not the current golden set).
- Reranker latency becoming user-visible at p99 under real traffic, at
  which point a distilled reranker or a smaller candidate pool goes first.

# ADR-001: Hybrid retrieval architecture (BM25 + dense + cross-encoder rerank)

- Status: accepted
- Date: 2026-04-02
- Deciders: Peter (retrieval), Kenny (backend), David (full-stack)

## Context

Pure dense retrieval fails the moment someone searches for an exact document
number, product code, or legal clause. Dense embeddings capture semantic
similarity, but an exact term like "Section 3.1" or "RFC 7807" has no special
weight in embedding space: a paraphrase of a nearby concept can outrank the
document that literally contains the clause. On the legal/tech benchmark
corpus this showed up as exact-lookup queries returning conceptually adjacent
but wrong documents.

## Decision

Adopt a hybrid retrieval pipeline with three stages:

1. **Sparse leg (BM25)** over chunk text for exact term, code, and clause
   lookups — the failure mode of pure vector search.
2. **Dense leg (Qdrant)** over `all-MiniLM-L6-v2` embeddings for semantic
   recall on natural-language questions.
3. **Cross-encoder rerank** (`ms-marco-MiniLM-L-6-v2`) over the fused
   candidate set for final ordering.

The sparse and dense candidate lists are merged with Reciprocal Rank Fusion
(RRF) rather than raw score combination, because BM25 and cosine scores live
on incompatible scales. Each leg is min-max normalized before fusion.

## Alternatives considered

- **Dense-only retrieval.** Simplest operationally, but fails exact-lookup
  queries (clause numbers, product codes, RFC identifiers) where the exact
  token must match. Rejected: this is the failure mode we set out to fix.
- **BM25-only retrieval.** Excellent on exact terms, poor on paraphrases and
  natural-language questions. Rejected: semantic recall matters too much.
- **Learned fusion (LambdaMART-style).** Higher ceiling, but needs labelled
  training data we do not have yet. Rejected for now; RRF with fixed weights
  is a strong, label-free baseline and the fusion weights are isolated behind
  configuration if we revisit this.

### Why not just tune the dense model?

Fine-tuning the embedder on legal text would close some of the exact-match
gap, but it cannot make an embedding *guarantee* token equality. Exact
lookup is a lexical constraint, not a semantic one — it belongs in the
sparse leg by design.

### Candidate pool sizing

Each leg contributes `candidate_k = 50` chunks to fusion. Grid search over
the golden set showed nDCG@10 flat between 40 and 80 candidates and a slow
decline past 100 (rerank cost grows linearly), so 50 is the default.

### Chunking interacts with fusion

Clause-aware chunking is a precondition for the sparse leg to work: a
fixed-size window that cuts "Section 3.1" in half makes the exact term
unfindable no matter how good BM25 is. See the 2026-04-22 chunking fix for
the recall numbers behind this.

### Why a cross-encoder instead of a bi-encoder rerank

A second bi-encoder pass would only re-rank by the same signal the dense leg
already used. The cross-encoder sees query and document *together*, which is
strictly more expressive — the standard accuracy/latency trade, accepted
here because we only rerank 50 candidates.

### Failure modes we accepted

- Queries mixing exact terms and conceptual language get whichever leg
  fires; RRF merges rather than reconciles them.
- BM25 tokenization keeps hyphenated terms whole, so hyphenated/unhyphenated
  variants of the same term can miss each other (tracked as a follow-up).

## Consequences

**Positive.**
- Exact-lookup queries (clauses, codes, RFC numbers) now hit the containing
  document via the sparse leg.
- Natural-language questions keep dense semantic recall.
- The cross-encoder rerank cleans up ordering on the fused candidate set,
  which is where most of the nDCG gain comes from.

**Negative.**
- End-to-end latency grows: the rerank stage dominates the budget.
- Three models/indexes to operate instead of one (BM25 index, Qdrant
  collection, cross-encoder).

**Latency budget (p95, measured on the benchmark corpus).**

| stage | p50 (ms) | p95 (ms) |
|---|---|---|
| embed query | 9 | 12 |
| sparse search | 3 | 4 |
| dense search | 14 | 18 |
| RRF fusion | 1 | 2 |
| rerank (top 50 -> 12) | 41 | 55 |
| **total (hybrid)** | **68** | **91** |
| dense-only total | 23 | 30 |
